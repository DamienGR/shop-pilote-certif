# Socle v0.3.2

Cette version corrige ce que l'étape 2 de la certification (jalon 10,
`docs/certification/plan.md`) a trouvé en créant les deux premières boutiques
réelles, et ce que le premier Nightly a trouvé dans les dépendances. Aucune
doublure ne voyait ces défauts : ils n'existent que dans un vrai dépôt de
boutique, sur un vrai poste.

## Ce qui change

- **la CI d'une boutique réelle est verte à sa première pull request.** Deux
  causes, présentes dans toute boutique créée depuis `v0.3.1` ou avant :
  - le test de `shopctl doctor` exigeait zéro contrôle rouge, alors que le
    checkout de CI d'une boutique n'a que `origin` et que `doctor` signale à
    raison l'absence de `core`. Le test écarte cet état du clone ;
  - le thème propre d'une boutique n'avait pas de signature de design, et
    n'avait aucun endroit à lui où l'écrire : `test/` appartient au socle. La
    signature d'un thème de boutique vit désormais dans
    `client/signatures/<thème>.json` ; celles des thèmes livrés restent dans
    `test/browser/__signatures__/`. `shopctl new` copie celle du thème de
    référence avec le thème ;
- **`shopctl repo` lit le protocole que `gh` a retenu pour github.com.** Il
  lisait la clé globale, que `gh auth login` laisse à `https`, et posait un
  remote HTTPS sur un poste qui n'a que SSH : le premier push demandait un mot
  de passe, dépôt déjà créé ;
- **`shopctl new` refuse un slug qui tombe sur un témoin du socle**
  (`pilot-fr`, `canary-minimal-staging`), code 3, avant de cloner : une telle
  boutique échouait à sa propre porte du manifeste aussi longtemps qu'elle
  vivait. Le manifeste généré n'écrit plus « PLACEHOLDER » à côté d'un domaine
  passé par `--domain` ;
- **dépendances** : l'audit du Nightly (`npm audit --omit=dev
  --audit-level=high`) est vert pour la vitrine et le MCP ; Astro 7.3,
  `@astrojs/cloudflare` 14.3 et Playwright 1.63 ;
- **CI du socle** : le job *Generated shop* retire le remote `core` avant les
  portes de la boutique, comme un vrai checkout.

## Migrations

**Aucune.** Les quarante-trois migrations de `v0.3.1` sont celles de `v0.3.2`.

## À faire dans la boutique

- une boutique dont le thème est le sien (créée par `shopctl new`, donc toutes
  sauf celles qui gardent un thème livré) : ajouter dans la pull request de
  mise à niveau `client/signatures/<thème>.json`, copie de
  `test/browser/__signatures__/<thème de référence>.json` si le thème n'a pas
  été retouché depuis sa création ; sinon l'enregistrer :
  `THEME=<thème> UPDATE_SIGNATURE=1 npm run test:browser -- design-signature`,
  et relire le diff comme du code ;
- un poste où `gh` pousse en SSH et dont la boutique a un `origin` HTTPS posé
  par `shopctl repo` : `git remote set-url origin git@github.com:<dépôt>.git` ;
- sinon, rien.

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.1 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.2` tout seul.

Aucune migration n'étant appliquée, un rollback applicatif vers `v0.3.1` reste
possible sans intervention sur la base.
