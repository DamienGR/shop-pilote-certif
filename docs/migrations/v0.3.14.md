# Socle v0.3.14

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version ferme ce que la répétition de l'étape 9 de la certification
(jalon 10, `docs/certification/plan.md`) a trouvé sur le chemin de la mise en
production : deux portes ouvertes au public le jour du premier déploiement, un
domaine d'images rendu là où il ne sert pas, et un nocturne qui ne tenait plus
le RPO une fois le staging détruit. La checklist de lancement de chaque
boutique est désormais `docs/operations/mise-en-ligne.md`.

## Ce qui change

Outillage :

- **`shopctl admin password --env <env>`** pose le mot de passe de
  l'administration, lu sur l'entrée standard (saisi deux fois sans écho, ou
  depuis un fichier), haché par `src/features/auth/password.ts` et relu.
  Lancé après `provision` et avant le premier `deploy`, il referme
  l'assistant `/admin/setup` avant qu'il ne soit jamais ouvert au public ;
  c'est aussi la réinitialisation d'un mot de passe perdu, sans la fenêtre
  que `scripts/admin-reset.sh` ouvrait ;
- **`provision --env production` coupe le paiement de démonstration** tant
  que la boutique n'a jamais été installée : sans Stripe, une production
  publique prenait des commandes sans paiement. Le commerçant le rallume dans
  Réglages → Paiements ; une boutique installée n'est pas touchée. `restore`
  ne compte pas cette ligne quand il demande si sa cible est vide ;
- **`cloudflare.imagesDomain` n'est rendu que pour la production**, et
  `deploy --env production` refuse un domaine déclaré qui n'est pas attaché au
  bucket d'images. `provision` rappelle de l'attacher ;
- **`shopctl repo` crée l'environnement GitHub `backup`**, sans relecteur et
  limité à la branche par défaut, et y pose `CLOUDFLARE_API_TOKEN_BACKUP`, le
  compte de la production et la clé de sauvegarde. Il refuse d'y poser un
  jeton qui déploie ;
- **le `Nightly` sauvegarde la production** chaque nuit dans cet
  environnement (`backup --env production --upload`, puis `backup verify`),
  et **cesse d'interroger un staging détruit** quand la variable de dépôt
  `STAGING_RETIRED` est posée — `destroy --env staging` le rappelle ;
- **la porte distante accepte une boutique sans moyen de paiement**, dont
  `/express` renvoie vers la boutique, et le dit ;
- **`destroy` nomme le vidage d'un bucket dans le tableau de bord** pour les
  clés que personne n'a imprimées.

Documentation : la checklist de lancement ; le runbook du mot de passe perdu
réécrit autour de `admin password` ; les droits du jeton de sauvegarde
nocturne.

## Migrations

- aucune.

## À faire dans la boutique

- relancer `shopctl repo --reviewer <login>` pour créer l'environnement
  `backup`. Avant la mise en ligne, il reste vide et le job de sauvegarde
  nocturne de la production le dit dans un avertissement ; après, exporter
  `CLOUDFLARE_API_TOKEN_BACKUP` (un jeton du compte de production : D1 en
  lecture, Workers R2 Storage en écriture, Account Settings, Memberships et
  User Details en lecture) et relancer `shopctl repo` ;
- une boutique dont le manifeste déclare `cloudflare.imagesDomain` : vérifier
  qu'il est attaché au bucket d'images de la production, sans quoi le
  prochain `deploy --env production` refuse. Son staging sert désormais ses
  images par le Worker ;
- une boutique dont le staging est déjà détruit :
  `gh variable set STAGING_RETIRED --body <date>`.

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.13 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.14` tout seul.

Aucune migration, rien ne change dans le code du Worker : un rollback
applicatif vers `v0.3.13` reste possible sans intervention sur la base.
