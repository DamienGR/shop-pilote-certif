# Socle v0.3.3

Cette version corrige ce que l'étape 3 de la certification (jalon 10,
`docs/certification/plan.md`) a trouvé : quatre trous trouvés en répétition,
contre une doublure de wrangler qui voit deux comptes, puis deux trouvés en
réel, sur le staging de `pilote-certif` et sur le poste de l'opérateur. Elle
fait tomber les quatre contournements de la
[fiche de l'étape 3](../certification/etape-3-commandes.md).

## Ce qui change

- **l'administration d'un Worker sans cache enregistre sans erreur.** Un
  Worker déployé avec `cache.enabled: false` — toute instance neuve, et toute
  preview de staging — reçoit de `cloudflare:workers` un `cache` sans méthode
  `purge`. Le socle y voyait une purge échouée et répondait 500 après
  l'écriture en D1 : « Internal error » sur `/admin/setup`, « Save failed »
  partout ailleurs, données pourtant enregistrées. Sans cache, les purges ne
  font plus rien ;
- **`shopctl` passe à wrangler le compte qu'il a vérifié.** Avec une session
  qui voit deux comptes — l'agence invitée sur le compte du client
  (ADR 0015) —, wrangler refusait de choisir, ou prenait le compte qu'il avait
  en cache : `provision` aurait pu créer la boutique sur le mauvais compte en
  annonçant le bon. `catalog import --remote` passe par la même résolution ;
- **le test de fumée de `deploy` interroge l'origine du manifeste**, plus une
  URL lue dans la sortie de wrangler, qui n'en donne aucune exploitable
  derrière un domaine personnalisé ;
- **`deploy --json` ne rend que le rapport sur la sortie standard** ; la
  sortie de `npm run verify` et du build passe sur la sortie d'erreur ;
- **le contrôle d'e-mail du nocturne passe Turnstile** quand le widget porte
  les clés de test de Cloudflare, et se saute en le disant devant un widget
  réel ;
- **`shopctl doctor` vérifie la session Cloudflare comme `provision`**, par
  `wrangler whoami --json` : sans `--json`, wrangler 4.149 sort en 0 quand
  personne n'est connecté, et `doctor` déclarait la session active ;
- **porte de propriété** : un fichier du socle apporté tel quel par une
  release fusionnée n'est plus une divergence de la boutique ; une montée de
  version ne demande plus le label `core-change`.

## Migrations

**Aucune.** Les migrations de `v0.3.2` sont celles de `v0.3.3`.

## À faire dans la boutique

- une boutique dont le staging a les clés de test de Turnstile : cocher
  « Enable Turnstile » dans Admin → Réglages → Protection après le
  déploiement ;
- sinon, rien. Les contournements de la fiche de l'étape 3
  (`CLOUDFLARE_ACCOUNT_ID` exporté, `--url`, `--skip-verify --skip-build`)
  restent acceptés, mais ne sont plus nécessaires.

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.2 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.3` tout seul.

Aucune migration n'étant appliquée, un rollback applicatif vers `v0.3.2` reste
possible sans intervention sur la base.
