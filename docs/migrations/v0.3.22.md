# Socle v0.3.22

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version corrige les deux défauts trouvés en répétant l'étape 10 de la
certification, le passage à l'argent réel (jalon 10,
`docs/certification/plan.md`). Le premier aurait coûté de l'argent à un
commerçant : une production tenant une clé Stripe de test prenait des
commandes payées par une carte de test.

## Ce qui change

- **Chaque environnement a son mode Stripe.** Stripe tient le mode test et le
  mode live comme deux mondes séparés, qui répondent pareil : une clé de test
  ouvre une session, la carte `4242 4242 4242 4242` la paie, et le webhook
  signé dit `paid`. Collée dans une production, une clé de test donnait donc
  une commande, un e-mail « Nouvelle commande » au commerçant et une unité de
  stock en moins, pour un paiement qui n'existe pas. Le Worker ne savait pas
  qu'il était la production. Le rendu du manifeste (`provision`, `deploy`,
  `prepare-client --env`) écrit désormais `MINSHOP_ENV` dans ses `vars` :
  `production`, `staging`, ou vide pour un rendu qui n'atteint aucun compte
  (témoins, développement local, `provision-cf.sh`). La production n'accepte
  que le mode live, le staging que le mode test, et un rendu vide les deux
  (`src/features/payments/stripeMode.ts`). Trois endroits le lisent :
  - **Réglages → Paiements → Carte (Stripe)** refuse à l'enregistrement une clé
    de l'autre mode, une clé publiable (`pk_…`) et un secret de signature qui ne
    commence pas par `whsec_`. Rien n'est enregistré, la paire en place reste.
    La carte dit le mode de la clé enregistrée (« En service — mode live :
    paiements réels »), sans jamais montrer la clé ;
  - **le prestataire Stripe** ne se construit pas sur une clé de l'autre mode,
    enregistrée avant cette version : le paiement par carte est hors service,
    et la carte de Réglages dit pourquoi ;
  - **le webhook** refuse, signature vérifiée, un événement de l'autre mode
    (400). Un endpoint de test pointé sur une production signe ses événements
    comme un autre.
- **L'alerte « Nouvelle commande » numérote la commande comme le reste.** Elle
  portait l'identifiant de ligne de la base : « n°1 » dans l'alerte du
  commerçant, « n°2vgje1r0cb » dans l'e-mail du client, l'administration et
  l'export. Elle prend le numéro de la commande, et son objet perd le
  `- ord_…` qui le répétait : `Nouvelle commande <boutique> n°<numéro>`. L'identifiant
  public reste dans le corps, avec le lien vers l'administration.

Nouvelle porte : `test/integration/stripe-mode.mjs`, sur le Worker construit,
en production, en staging et sans environnement.

## Migrations

- aucune.

## À faire dans la boutique

- **avant de déployer** chaque environnement : Admin → Réglages → Paiements,
  la clé Stripe doit être une clé live en production et une clé de test en
  staging. Une clé de l'autre mode met le paiement par carte hors service au
  déploiement suivant : la remplacer d'abord. `MINSHOP_ENV` n'arrive qu'avec ce
  déploiement ; jusque-là, le Worker en place accepte les deux modes ;
- **après le déploiement** : la carte Stripe de Réglages dit « mode live » en
  production, « mode test » en staging ;
- **un filtre de messagerie** qui attend `- ord_` dans l'objet de l'alerte doit
  prendre le numéro (`n°…`), ou chercher l'identifiant dans le corps.

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.21 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.22` tout seul. Le
`wrangler.jsonc` re-rendu gagne la ligne `MINSHOP_ENV`, et la porte de
propriété le laisse passer (`v0.3.20`).

Aucune migration : un rollback applicatif vers `v0.3.21` reste possible sans
intervention sur la base ; l'ancien Worker ignore `MINSHOP_ENV`.
