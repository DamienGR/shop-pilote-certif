# Socle v0.3.13

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version ferme ce que le passage réel de l'étape 8 de la certification
(jalon 10, `docs/certification/plan.md`) a trouvé : une restauration vers un
autre compte qui ne passait pas telle qu'écrite, et trois messages qui
cachaient leur cause.

## Ce qui change

Outillage :

- **Les tests ne voient plus le shell de l'opérateur.** `deploy` relance la
  suite par `npm run verify`, depuis un shell qu'une fiche ou un runbook vient
  de remplir. Une clé exportée (`SHOPCTL_BACKUP_KEY`, comme la restauration
  vers un autre compte la demande) gagnait les commandes testées, huit tests
  rougissaient et `deploy` s'arrêtait sans rien téléverser. Les harnais vident
  désormais chaque variable que lit `shopctl` : la clé, les jetons par
  environnement, le compte, le suffixe de domaine ;
- **un échec de wrangler relaie la phrase de l'API et son code**, plus la
  ligne qui annonce l'échec. « Trigger configuration … was only partially
  updated: » devient la raison et son remède, par exemple « You need a
  workers.dev subdomain in order to proceed … [code: 10063] » ;
- **un jeton que `wrangler whoami` refuse nomme les droits qui lui manquent**
  (« Account Settings », « Memberships », « User Details », en lecture), au
  lieu de renvoyer vers `wrangler login`. `shopctl monitor --help` liste les
  droits de son jeton : il sert aussi à `whoami` et `d1 list` ;
- **l'anonymisation clôt les notifications de la personne encore en
  attente.** Le cron les retentait vers le pseudonyme ; elles passent à
  `skipped` dans la même instruction que l'effacement, et celles déjà
  envoyées gardent leur historique.

Documentation : ouvrir une fois Workers & Pages sur un compte neuf (sans
sous-domaine workers.dev, Cloudflare refuse le cron après le téléversement) ;
les droits du jeton de lecture de la production ; `wrangler.jsonc` à remettre
après la remise à zéro du mot de passe.

## Migrations

- aucune.

## À faire dans la boutique

- rien dans le dépôt. Le jeton `MONITOR_CLOUDFLARE_API_TOKEN`, s'il existe,
  doit porter les droits que `shopctl monitor --help` liste ; avec « Account
  Analytics » seul, le contrôle nocturne de la production s'arrête sur
  « wrangler refuse le jeton ».

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.12 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.13` tout seul.

Aucune migration, rien ne change dans le Worker : un rollback applicatif vers
`v0.3.12` reste possible sans intervention sur la base.
