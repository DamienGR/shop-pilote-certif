# Socle v0.3.16

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version ferme le défaut que le passage réel de l'étape 9 de la
certification (jalon 10, `docs/certification/plan.md`) a trouvé dans Admin →
Réglages : le navigateur versait le mot de passe de l'administration dans un
champ de clé, et l'enregistrement remplaçait la clé par lui.

## Ce qui change

Administration :

- **les champs de clé du coffre ne reçoivent plus le mot de passe enregistré
  par le navigateur.** `SecretField` rendait chaque clé (Resend, Turnstile,
  Stripe, Shippo, OpenNode, LNbits, phoenixd) en `type="password"` avec
  `autocomplete="off"`, que les navigateurs ignorent sur un champ mot de
  passe : le mot de passe de la connexion y apparaissait, surtout derrière un
  champ texte (l'expéditeur, la clé de site Turnstile). Enregistrer la
  section, pour changer un autre réglage, remplaçait la clé par ce mot de
  passe sans rien dire, et la boutique l'envoyait ensuite au fournisseur comme
  jeton : le pilote a vu Resend refuser son e-mail de test (400), et une clé
  Stripe aurait arrêté les paiements. Le champ demande désormais
  `autocomplete="new-password"`, avec les attributs que 1Password, LastPass,
  Bitwarden et Dashlane lisent pour s'abstenir ;
- **le serveur refuse une clé qui est le mot de passe de l'administration**
  (`src/features/secrets/submitted.ts`) : il garde la clé enregistrée,
  enregistre le reste de la section, et le dit. La comparaison coûte un
  PBKDF2 par clé non vide, à l'enregistrement seulement.

## Migrations

- aucune.

## À faire dans la boutique

- dans Admin → Réglages, **éprouver chaque moyen configuré** : une clé déjà
  remplacée par le mot de passe ne se répare pas toute seule. Envoyer un
  e-mail de test ; pour Stripe, un checkout de test ; pour Turnstile, une
  connexion. Si l'un échoue, saisir à nouveau la clé du fournisseur ;
- si une clé a été remplacée, le mot de passe de l'administration est parti
  chez ce fournisseur : le changer (`shopctl admin password --env <env>`).

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.15 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.16` tout seul.

Aucune migration : un rollback applicatif vers `v0.3.15` reste possible sans
intervention sur la base.
