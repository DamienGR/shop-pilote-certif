# Socle v0.3.23

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version corrige les deux défauts trouvés en passant l'étape 10 de la
certification en réel (jalon 10, `docs/certification/plan.md`) : l'un sur le
poste de l'agence, à la montée de version, l'autre dans l'administration, au
moment de saisir la clé Stripe de la production.

## Ce qui change

- **Réglages dit pourquoi il refuse un enregistrement.** Avec JavaScript, une
  section s'enregistre en arrière-plan. Le serveur répondait à un refus par sa
  raison, et le script la jetait pour afficher « Échec de l'enregistrement —
  réessayez ». La production refusait ainsi une clé Stripe de test sans le
  dire, et réessayer n'y change rien. C'était vrai de tous les refus de
  Réglages : clé de l'autre mode, clé publiable, secret de webhook, fuseau
  horaire, champ prérempli par le navigateur. La raison s'affiche désormais
  sous le formulaire, et y reste jusqu'au prochain enregistrement. Une panne
  qui n'est pas un refus garde le message générique. Sans JavaScript, rien ne
  change : la page se ré-affiche avec la raison, comme avant.
- **`shopctl core upgrade` part de la version où la boutique se trouve.** La
  version d'une boutique se lit dans son historique, au dernier tag du socle
  fusionné. Or un clone ne connaît que les tags qu'il a récupérés, et une
  montée fusionnée sur GitHub puis tirée de l'origin de la boutique n'en
  apporte aucun. `core upgrade` lisait cet historique avant de récupérer les
  tags. Sur un clone resté à v0.3.5, la pull request annonçait donc
  « v0.3.5 → v0.3.22 » pour une boutique en v0.3.20, avec les notes depuis
  v0.3.6, 283 fichiers « divergents » et une migration déjà appliquée. La
  fusion elle-même était juste, seul le compte rendu était faux. Les tags sont
  maintenant récupérés d'abord.
- **`shopctl core status` nomme le tag qui manque au clone** au lieu de mettre
  en cause le manifeste. Il disait « le manifeste déclare 0.3.20 et
  l'historique porte v0.3.5 », ce qui invite à remettre une version fausse
  dans un manifeste juste. Il ajoute désormais « ce clone n'a pas le tag
  v0.3.20 », avec la commande `git fetch --tags core`. `fleet status` et
  `fleet verify` disent la même chose.

Nouvelle porte : `test/browser/admin-settings.spec.mjs`, Réglages avec son
script, sur le Worker construit. Le jeu d'essai de la porte navigateur a
désormais un mot de passe d'administration et un coffre.

## Migrations

- aucune.

## À faire dans la boutique

- rien. Une pull request de montée ouverte avant cette version depuis un clone
  aux tags en retard peut annoncer une mauvaise version de départ : la relire
  après un `git fetch --tags core`, et récrire son corps si besoin. Le diff,
  lui, est juste.

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.22 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.23` tout seul.

Aucune migration : un rollback applicatif vers `v0.3.22` reste possible sans
intervention sur la base. L'ancien Worker ignore l'en-tête de refus, et son
script affiche le message générique comme avant.
