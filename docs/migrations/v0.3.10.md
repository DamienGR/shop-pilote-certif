# Socle v0.3.10

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version ferme ce que la répétition de l'étape 7 de la certification
(jalon 10, `docs/certification/plan.md`) a trouvé avant tout passage en réel :
deux boutiques sur un même compte, la seconde déployée sur workers.dev, puis
supprimée. Quatre défauts de `shopctl`, que la fiche de l'étape aurait tous
rencontrés.

## Ce qui change

Outillage :

- **le premier déploiement d'une boutique sans Access n'échoue plus.** Tant
  que l'assistant `/admin/setup` n'a pas tourné, la vitrine renvoie chaque page
  vers lui : le test de fumée de `shopctl deploy` lisait ces redirections
  comme une vitrine absente (« la liaison D1 est le premier suspect ») et
  finissait en code 6, après le téléversement. Cela touchait tout staging
  servi sur workers.dev et la **première production de chaque boutique**. La
  redirection vers l'assistant est désormais un avertissement qui dit l'état
  de la boutique ; elle prouve au passage que la base a répondu. L'alerte sur
  l'assistant ouvert reste, jusqu'à ce que le mot de passe soit posé ;
- **`shopctl destroy` supprime le namespace KV des sessions.** L'adaptateur
  Astro lie `SESSION` dans la configuration construite et wrangler le crée au
  premier déploiement, sous `<worker>-session` ; aucun fichier de la boutique
  ne le nomme, et `destroy` le laissait sur le compte après tout le reste.
  Il est cherché par ce nom, et supprimé juste après le Worker ;
- **la commande que `destroy` propose pour vider un bucket porte `--remote`.**
  Sans lui, wrangler 4 vide son simulateur local, annonce « Delete complete »,
  et le bucket du compte reste plein ;
- **un import distant refusé renvoie vers `shopctl provision`.** Le refus
  d'un `wrangler.jsonc` rendu pour une autre boutique conseillait
  `prepare-client.mjs --env`, qui rend les bons noms autour d'un identifiant
  de base factice : l'import passait le contrôle puis échouait chez wrangler.
  `provision` rend l'identifiant réel et ne crée rien sur un environnement
  déjà provisionné.

Portes :

- la porte d'isolation (`npm run test:tenant-isolation`) supprime le staging
  de la canari à côté du pilote, et vérifie que seules ses six ressources ont
  quitté le compte ;
- la doublure de wrangler crée le namespace des sessions au déploiement, et
  traite `r2 object`, `d1 execute` et `d1 migrations` en local sans
  `--remote`, comme wrangler 4.

## Migrations

- aucune.

## À faire dans la boutique

- rien. Le jeton API de chaque environnement, créé depuis le modèle « Edit
  Cloudflare Workers », porte déjà « Workers KV Storage » en écriture, dont
  `destroy` a besoin ; un jeton taillé plus court doit l'ajouter.

## Compatibilité

Le manifeste ne change pas : un manifeste v0.3.9 reste valide tel quel, et
`shopctl core upgrade` met `coreVersion` à `0.3.10` tout seul.

Aucune migration, rien ne change dans le Worker : un rollback applicatif vers
`v0.3.9` reste possible sans intervention sur la base.
